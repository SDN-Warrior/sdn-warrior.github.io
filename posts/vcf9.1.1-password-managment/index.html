VCF9.1.1 - Password Managment

Passwords: the admin's bane. Everyone hates them, but they have to be done. Since VCF comes with a bunch of passwords and a bewildering number of options, I'll try to shed some light on the chaos here.

Introduction

My favorite topic after certificates is, of course, passwords, and since VCF has always had a habit of forcing you to change your password – and since VCF 9.x does things a bit differently – it’s time to take a closer look at this topic. A little spoiler: it won’t be easy. But all in good time – I’m trying to shed a little light on the password jungle here and show what works, what doesn’t, and what you can do.

Not all passwords are the same.

First, we need to determine which password or type of account we’re talking about. There are, in fact, three different types of accounts.

Account Type Description Notes
Local (OS) accounts Accounts provisioned directly in the operating system of a virtual appliance, primarily used for secure shell (SSH) access. Examples: root, vcf
Application accounts Accounts provisioned for interactive logins with access to the application’s UI and API. Some VCF components also use application accounts, such as administrator@vsphere.local, for inter-component communication.
Service accounts System-managed accounts provisioned for inter-component communication. Passwords are managed through automated mechanisms. Examples: svc-vcf-*, svc-sddcm-*

By the way, this is an official classification by Broadcom. And since we have a hodgepodge of very different products here, all of which were marketed under the VCF umbrella, we naturally don’t have a standardized way to manage the passwords. But to be fair, it has improved with VCF 9.1. Now that we’ve clarified that, we can take a look at the tools VCF provides for reading or changing passwords.

Password Management in SDDC Manager

Yes, the SDDC is still an important component in VCF 9.1.x – they say it’s dead, but it’s still going strong. The SDDC offers us various options. Maybe I’ll start with the simple UI options. Three types of actions are supported: rotate, remediate, and update. Remediate and update are often confused. An update sets a new password; this requires both the old and the new password. Remediate changes the password in the database if a password has been changed outside the SDDC workflow or if a password is marked as “disconnected” for any reason. Manual password rotation via the UI and via the API is supported for the following accounts:

Password Rotation via SDDC Manager UI

Scheduled Password Rotation via SDDC Manager UI

In addition to manually controlled password rotation, the SDDC also supports automated password rotation.

VCF Component Managed Accounts Supported Rotation Intervals
vCenter Server root 30, 60, or 90 days
NSX Manager root, admin, audit 30, 60, or 90 days

Note: Custom intervals are also possible, but not through the UI.

Info
Unfortunately, it is not possible to enable automatic password rotation for ESX servers; this feature has not been supported for quite some time and, unfortunately, has not yet been brought back.

Additional Service Accounts Exposed via SDDC Manager API

In addition to the passwords that can be managed in the UI, there are other service passwords that can only be rotated or updated via the API.

Just for testing purposes, I’ll show an example of a rotate operation via the API here. Since I’m lazy, I used the graphical tools in the SDDC Manager. To perform the rotate, you need a CredentialsUpdateSpec, which must be included as a JSON body. The API endpoint is PATCH /v1/credentials. An example spec would look like this:

{
  "operationType": "ROTATE",
  "elements": [
    {
      "resourceName": "esx01.lab.sdn-warrior.cloud",
      "resourceType": "ESXI",
      "credentials": [
        {
          "credentialType": "SSH",
          "accountType": "SERVICE",
          "username": "svc-vcf-esx01"
        }
      ]
    }
  ]
}

Of course, you can also use the same method to update and reset a password. I’ve provided the specifications for a root account here.

Update

SDDC local users

The local SDDC users vcf, root, and backup can be modified via the separate API endpoint PATCH /v1/sddc-manager/local-os-user-accounts , provided they have not yet expired. Of course, we need a customized spec here, and only updates are supported.

{
  "username": "root",
  "oldPassword": "<CURRENT_ROOT_PASSWORD>",
  "newPassword": "<NEW_ROOT_PASSWORD>"
}

If you missed the deadline and your local root or vcf user account has already expired, here are the official recovery instructions via the VM console. https://knowledge.broadcom.com/external/article/323984/how-to-reset-sddc-manager-vcf-and-root-u.html

Retrieve a password using SDDC Manager

This topic is certainly not new to you – for all accounts that I can manage via the SDDC Manager, I can, of course, also retrieve the password. This can be done either via the API endpoint GET /v1/credentials/ or via the lookup_passwords function on the SDDC Manager (via ssh) itself, provided you haven’t locked out the VCF user.

Info
Passwords for local SDDC accounts cannot be retrieved this way.

What can VCF Operations do for me?

Well, at first glance, to be honest, not much. But on closer look, it’s a little more than I’d thought. In principle, VCF Operations can unfortunately only update passwords. No remediation, no rotation – which I personally find quite unfortunate. But Operations can, for example, update the root or VCF account of the SDDC Manager. So this might save you some API work, provided you still have the old password. In addition, for some service accounts, the password can be rotated via the integration if system-managed accounts are used. This is the default for greenfield deployments, but is generally not the case for brownfield deployments and should be changed.

Passwords in VCF Operations
Rotate System Managed Accounts

However, when changing a password via Operations, the password policy is automatically enforced and verified. Operations itself does not store any passwords, and as far as I know, there is no way in version 9.1.1 – not even via the internal API – to have Operations display a password. If you want to automate password management, you’ll have no choice but to use an external secret vault where passwords are stored so that you can change them programmatically via the API. In version 9.1, CyberArk is directly supported via plugin integration in Operations, but since I don’t have CyberArk in my lab, I haven’t been able to test this yet.

Password Policys

VCF 9.1 introduces another feature: password policies. This feature allows a password policy to be applied either fleet-wide or separately across VCF instances and VCF Management (fleet components). The feature can be found under Manage -> Fleet Management -> Passwords -> Password Policy in VCF Operations. You can configure the minimum password length, character limits, account lockout parameters, and password expiration. By the way, this is a very convenient way to avoid having to constantly deal with expired passwords in the lab, especially when it’s not always turned on.

Personal Thoughts

As someone who’s once again dealing more frequently with operational issues, I have to say that I don’t think the password management solution is well-designed. It’s still very clear here that VCF 9 needs to be more tightly integrated. The fact that there’s no way to perform a password rotation via the Operations UI or API is also very frustrating.

On the other hand, I really like the password policy, although I’d like to see a bit more granularity so that the policy could perhaps be broken down to the cluster level. It’s clear that in 2026, passwords are still no fun, and the flood of accounts within VCF doesn’t make things any easier.

If anyone knows a way to retrieve the passwords through Operations, please send me a message. Cheers!
