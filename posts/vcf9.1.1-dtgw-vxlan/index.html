VyOS EVPN Fabric

A short disclaimer
My EVPN fabric is set up so that I can demonstrate all the features from an NSX perspective; it does not represent an ideal configuration as one would use in practice. However, since resources in the lab are limited, and I didn’t want to run multiple VyOS routers on a single Proxmox host – partly due to Layer 2 virtualization – and to avoid issues with the hypervisor’s virtual switches, the EVPN fabric should be viewed as an optimized test setup rather than a design recommendation.

Now that that’s clear, we can take a closer look at the test setup. For my tests, I need an external EVPN/VXLAN fabric that will represent a physical network fabric. Since my MikroTik switches currently don’t support Type 5 routes, I decided to use a fabric based on VyOS VMs. I’m using two Proxmox servers running on Intel NUCs. These aren’t in a cluster, so test VMs can’t migrate between the hosts. Why Proxmox? It’s relatively simple – I don’t have enough vSphere licenses. For the functionality I need – namely, hosting a VyOS router and one test VM per server – this isn’t a problem. Since the setup is a bit more complex, I’m trying to break it down into smaller parts so I can gradually work my way toward the big picture. That’s why, at this point, I’ll focus only on the VXLAN fabric and won’t go into detail about the route controller setup just yet.

Component Role IP Address BGP AS

Alpine-PR-01 Test VM connected to VyOS-01 192.168.250.10/24 —

The VyOS-01-BGW router serves a dual role. It acts as a leaf, connecting the Alpine-PR-01 test VM to the client network, while also functioning as a border gateway, thereby serving as the central BGP peering point with the NSX route controllers.

VyOS-02 is only a leaf for Alpine-PR-02. In addition, EVPN information is exchanged via an iBGP session (L2VPN EVPN) with VyOS-01-BGW (AS 64515).

The VXLAN configuration uses two VNIs: a Layer 2 VNI (65260), which extends the client segment across both routers, and a Layer 3 VNI (65000), which is associated with the “Tenant” VRF and provides the routing context. Each VNI is connected to its own Linux bridge. For the L2 VNI, I used a static VXLAN remote VTEP for simplicity. The Linux bridge for the L2 VNI is also assigned to the “tenant” VRF so that later, both the test VMs on the physical side and the test VMs in the VPC will belong to the same routing context. Both routers use different export targets, and each imports all routes from the other router. The topic of route targets will become important again later when it comes to configuring the route controller.

Route Controller in 9.1.1

One of the cool new features is that the Route Controller now supports active/active mode and can scale out to up to 8 nodes. To use this effectively, you need at least two BGW routers. In my setup, I’m using just one router that has MP-BGP peering with both Route Controllers. Not ideal, but hey, it’s a lab.

In general, however, there are a few limitations or prerequisites. In active/active mode, only one MP-BGP interface per Route Controller can be used, even if a Route Controller has three interfaces. A non-configurable interface handles the notification messages during a vMotion operation. Another interface is used for management traffic. This means all three interfaces are in use. The physical fabric must continue to announce a default route, even when fancy features like Direct Prefix Routing are used - I’ll explain what that is later.

Design Decisions for Active/Active

Unlike in active/standby mode, no floating IP is used for the MP-BGP session. This means that the route controllers can be located in independent L3 segments and do not require a shared L2 infrastructure. As for the failure domain, Broadcom recommends using different ESX servers in different clusters and racks (if possible). At least two peerings to external BGW routers per route controller are recommended. ECMP with individual gateway VTEPs is possible. For BGP, the default values of 60/180 seconds are sufficient when BFD is used. While BFD is prohibited in active/standby mode, it is highly recommended in active/active mode.

Direct Prefix Routing

Strange name, big difference in the data path. The feature was just released in 9.1.1, and it changes quite a bit. In the 9.1 distributed VXLAN connectivity model, traffic between the virtual and physical fabrics was always routed through the BGW routers. With DPR, you can now change this. When this feature is enabled, the route controllers can receive and process specific host routes via the MP-BGP session. In 9.1, only a default route was accepted. If you look at the forwarding table of the Distributed Transit Gateway on the ESX server, you’ll see the difference right away. Design Decisions Direct Prefix Routing

Of course, you shouldn’t use this feature across the board for everything. In a large fabric, routing tables can quickly become very large. Broadcom recommends using DPR for latency-sensitive traffic such as S3 or NFS. Additionally, you should define additional route targets for targeted import and export and configure them only on the relevant leaf switches. The additional route targets (RTs) must also be configured in the External Connection for the DTGW. You can see this in my screenshot of the External Connection. I created a separate RT (65000:20) specifically for DPR. Another recommendation is to set up prefix filters. Thanks to DPR, the RC also supports received Type 2 routes and translates them into host prefix forwarding entries for the DTGW on the ESX. Another important point is that each ESX server must be able to communicate with all relevant VTEP IP addresses on the leaf switches via its TEP network. Traffic that cannot be routed via DPR will continue to be routed through the BGW routers.

Now that we have the basics covered, we can expand the entire setup to include stateful services. Yes, you heard that right. VCF 9.1.1 now also supports stateful services using the Distributed VXLAN Connectivity Model.

VNA and Route Controller - its a perfect match

I’ve been waiting for this feature, and I had hoped it would be included in 9.1 when I checked out the RC. For anyone who doesn’t know what the VNA is, what it can do, or how it’s set up, I recommend reading this article and this one first.

VNA Support enables the following:

  • Default Outbound NAT (Auto-SNAT)
  • custom NAT
  • DHCP relay for external DHCP servers
  • load balancing

This also means that you can use VKS and Automation in “All Apps” mode, but setting that up is a topic for a separate blog post. Here, I’ll just show you how to make the VNA work in the distributed VXLAN model.

Unfortunately, you can’t simply enable stateful services on the Route Controller cluster. To do so, you must deploy a dedicated VNA cluster consisting of at least one VNA appliance. In my setup, I have therefore deployed a VNA node.

To use the VNA, you must configure it in the VPC connectivity profile. I encountered an error here and received the following error message:

This feature requires TN Minimum Version >= 9.1.1.0

My deployment was a greenfield 9.1.1 setup that I had previously patched to 9.1.1.0100. And so my environment should actually have met all the requirements.

KB Article 455545
There is a Knowledge Base article that describes my exact problem and helped me resolve the issue quickly. https://knowledge.broadcom.com/external/article/455545/cannot-configure-vpc-connectivity-profil.html In addition, the same solution is included in the design guide. https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/advanced-network-management/ethernet-vpn-evpn/distributed-vxlan-connection/enable-advanced-networking-services-for-distributed-vxlan-connections.html

To resolve the issue, simply set the TN version to 9.1.1.0 via the API.

PUT https://<nsx-mgr>/policy/api/v1/infra/sites/default/enforcement-points/default/host-transport-nodes/feature-opt-in 

{
   "host_tn_min_os_version": "9.1.1.0"
}

It took about 5 minutes before I was able to configure the VNA in the VPC Connectivity Profile. Once the VNA is configured in the profile, a service subnet is configured for the VPC gateway. Special Case: External IP

A quick note on external IPs: As you probably know, you can easily assign an external IP in vCenter by right-clicking a VM in a private segment. As soon as you do this, a reflexive 1-to-1 NAT is created on the ESX server, which automatically disables the default outbound NAT for the VM. As a result, a /32 route appears in VyOS for the external IP, pointing to the TEP IP of the ESX server on which the VM is running. Additionally, no traffic from this VM will pass through the VNA. This sounds good at first, but it comes with a drawback: reflexive NAT is stateless, meaning it exposes my VM and makes it more vulnerable since there is no session awareness, return traffic validation, and so on. Therefore, the recommendation is to use a combination of DNAT and SNAT instead if a VM in the private segment needs to be exposed, as this gives me more control. Of course, it always depends on the use case.

Conclusion

With VCF 9.1.1, connecting VPCs becomes even more flexible, but this comes at the cost of a certain degree of complexity. In my view, the VNA extension is what makes Distributed VXLAN Connectivity truly interesting, as it allows you to harness the full potential of VPCs and, thanks to DPR, gives you significant control over the actual data path. The active/active setup is also a much-needed enhancement and makes my architecture more flexible and robust. VCF 9.1.1 offers even more new features, but that’s a topic for another article.
